# План: четыре моста и шесть дополнительных инструментов для opencode

Контекст: в программе уже есть блок «6. Серверы MCP». Мосты для Android-эмуляторов (LDPlayer, BlueStacks) и OBS уже реализованы, их не трогаем. Нужно добавить четыре новых моста (браузеры, OmniRoute, DBHub, LMArena) по тому же принципу: программа сама ставит, настраивает и регистрирует MCP-сервер в конфиге opencode.

Общее правило для агента: перед реализацией сверься с актуальными README и версиями пакетов, флаги ниже даны как ориентир и могут измениться.

---

## 1. Мост для браузеров (Chrome, Firefox, Яндекс.Браузер, Edge)

**Цель.** Нейросеть в opencode управляет отдельным браузером на выбор пользователя, а не только встроенной headless-копией.

**Основа.** Playwright MCP (`@playwright/mcp`). Альтернатива — Puppeteer MCP, но он работает только с Chromium-браузерами.

**Что сделать.**
1. В программе добавить выбор браузера: Chrome, Edge, Яндекс.Браузер, Firefox.
2. Для Chrome и Edge использовать встроенный выбор браузера Playwright MCP (параметр `--browser` со значениями `chrome` и `msedge`).
3. Яндекс.Браузер построен на Chromium, поэтому запускать его через путь к исполняемому файлу (`--executable-path`) либо подключаться по CDP (`--cdp-endpoint`), запустив браузер с флагом `--remote-debugging-port=<порт>`.
4. Firefox поддерживается Playwright только в его собственной сборке, а подключиться к обычному установленному Firefox по CDP нельзя. Агенту нужно проверить, как это решается в актуальной версии, и честно показать пользователю ограничение, если подключение к его Firefox невозможно.
5. Предусмотреть отдельный профиль браузера для нейросети, чтобы она не лезла в личные вкладки и сессии пользователя. Режим «использовать мой браузер с моими сессиями» делать только как явный выбор.
6. Прописать сервер в конфиге opencode (`opencode.json`, раздел `mcp`), тип `local`, команда через `npx`, с нужными аргументами выбранного браузера.
7. Кнопка в блоке «Серверы MCP»: установить, включить, выключить, сменить браузер.

**Проверка.** Нейросеть открывает страницу в каждом из выбранных браузеров, делает скриншот и читает заголовок.

## 2. Мост OmniRoute

**Цель.** Нейросеть в opencode сама разворачивает OmniRoute (AI-шлюз, объединяющий провайдеров за одним адресом) и подключает провайдеров.

**Что сделать.**
1. Мост поднимает программу OmniRoute на компьютере пользователя: установка, запуск, проверка, что панель отвечает.
2. Отдельный скилл в opencode:
   - подключается к OmniRoute после запуска;
   - автоматически, без ручного шага пользователя, подключает всех бесплатных провайдеров, которые доступны в OmniRoute, при каждом развёртывании и при каждом перезапуске OmniRoute (включая случай, когда список бесплатных провайдеров у OmniRoute изменился с прошлого раза);
   - добавляет эти провайдеры в список провайдеров opencode;
   - умеет перезапускать программу OmniRoute, если она зависла или упала.
3. Порядок установки, команду запуска и адрес API агент берёт из README репозитория OmniRoute (автор diegosouzapw), а не придумывает.
4. Ключи и токены провайдеров хранить локально, в логи и в чат их не выводить.
5. Кнопка в блоке «Серверы MCP»: развернуть, запустить, перезапустить, показать статус.

**Проверка.** После запуска в панели OmniRoute видны подключённые провайдеры, а в opencode они появляются в списке и отвечают на тестовый запрос.

## 3. Мост для баз данных: DBHub

**Цель.** Нейросеть в opencode работает с базами данных через один универсальный MCP-сервер.

**Основа.** DBHub от Bytebase: открытый исходный код, один сервер для PostgreSQL, MySQL, MariaDB, SQL Server и SQLite. Запускается через `npx` или Docker, есть браузерный Workbench, где видно выполненный SQL.

**Что сделать.**
1. В программе добавить форму подключения: тип базы, строка подключения (DSN), имя источника.
2. Хранить подключения в конфиге DBHub (`dbhub.toml`, секции `[[sources]]`), для каждого источника задавать собственные лимиты, например режим «только чтение» и максимум строк в ответе.
3. По умолчанию включать режим «только чтение» и менять его только по явному выбору пользователя.
4. Прописать сервер в конфиге opencode (раздел `mcp`, тип `local`, запуск DBHub через `npx`, транспорт stdio).
5. Пароли от баз хранить локально и не показывать в логах.
6. Кнопка в блоке «Серверы MCP»: добавить подключение, проверить соединение, включить, выключить.

**Проверка.** Нейросеть получает список таблиц и выполняет безопасный `SELECT` на тестовой базе.

## 3а. Мост LMArena (LMArenaBridge)

**Цель.** Нейросеть в opencode получает бесплатный доступ к моделям сервиса Arena (LMArena, arena.ai), в том числе к стелс-моделям, которые там тестируются анонимно. Мост поднимает локальный сервер с OpenAI-совместимым API, а opencode подключается к нему как к обычному провайдеру.

**Основа.** LMArenaBridge. Есть несколько форков на GitHub: CloudWaddie/LMArenaBridge (самый заметный, заявляет экспериментальную поддержку стелс-моделей), lianues/lmarenabridge (FastAPI и WebSocket), hung319/lmarena2api и другие. Агент сам выбирает живой и поддерживаемый форк: смотрит дату последнего коммита, README и открытые проблемы. Это не официальный продукт Arena.

**Что сделать.**
1. Перед работой открыть README выбранного форка и взять оттуда порядок установки, команду запуска, адрес API и способ авторизации. Ничего не придумывать: при составлении плана подробности запуска не проверялись. По описанию форков, для работы нужен токен авторизации с сайта Arena, но точный механизм (токен, userscript, расширение браузера) агент берёт из README.
2. Мост поднимает программу на компьютере пользователя: установка, запуск, проверка, что локальный сервер отвечает.
3. Отдельный скилл в opencode:
   - подключается к мосту после запуска;
   - получает список доступных моделей, включая стелс-модели, если они там есть;
   - добавляет их в список провайдеров opencode;
   - умеет перезапускать мост, если он завис или упал, и подсказывает обновить токен, если он протух.
4. Токен и данные сессии хранить локально, в логи и в чат их не выводить, внести в `.gitignore`.
5. Кнопка в блоке «Серверы MCP»: развернуть, запустить, перезапустить, показать статус, обновить токен.

**Оговорки (показать пользователю в программе до первого запуска).**
- Мост работает через веб-сервис Arena, а не через официальный API. Такое использование может не соответствовать условиям сервиса, а доступ может перестать работать без предупреждения. Включать только по явному согласию пользователя, по умолчанию выключен.
- Поддержка стелс-моделей экспериментальная: набор моделей на арене меняется, а стелс-модели появляются и исчезают.
- Запросы уходят на сервис Arena, и на этой площадке их могут использовать для оценки и публикации результатов. Приватный код и секреты через этот мост отправлять нельзя, и окно должно говорить об этом прямо.
- Бесплатный доступ ограничен лимитами и защитой сайта (проверки на робота и подобное), поэтому нестабильность ожидаема.

**Проверка.** Мост запущен, в opencode появляются модели с арены, тестовый запрос на несложную задачу получает ответ. Если токен недействителен или сервис не отвечает, окно говорит об этом прямо, без зелёной отметки.

## 4. Дополнительные инструменты (rtk, caveman, pxpipe, auto-improve, greenlight, Qwen Code ревьюер)

**Зачем.** Чем меньше текста уходит в нейросеть и приходит обратно, тем дешевле и быстрее работа и тем медленнее заканчиваются лимиты. Эти три инструмента режут расход в разных местах и друг другу не мешают. Все три добавить в программу как отдельные включаемые опции.

### 4.1. rtk (rtk-ai/rtk), «вывод команд короче»
- **Простыми словами:** когда агент запускает команды в терминале, они выдают много лишнего текста (логи, длинные списки). rtk убирает лишнее до того, как этот текст попадёт нейросети.
- **Что сделать:** установить бинарник rtk по инструкции из README репозитория (порядок установки не придумывать), подключить его к opencode так, чтобы вывод bash-команд шёл через rtk. Добавить в программе переключатель «включить / выключить».
- **Проверка:** длинная команда (например, большой `git log`) даёт агенту заметно более короткий вывод.

### 4.2. caveman (JuliusBrussee/caveman), «ответы короче»
- **Простыми словами:** скилл, который просит нейросеть отвечать коротко и без воды, телеграфным стилем. Код при этом остаётся прежним, пропадают только вежливые вступления и лишние объяснения.
- **Что сделать:** установить командой `npx skills add JuliusBrussee/caveman`. Заранее проверить в README, поддерживается ли opencode. Если нет, перенести его правила в инструкции агента (AGENTS.md) вручную. Дать в программе выбор уровня («лёгкий / полный»), потому что полный режим бывает слишком жёстким.
- **Проверка:** на один и тот же вопрос ответ с включённым скиллом заметно короче, а код в нём тот же.
- **Оговорка:** цифры экономии (около 65–75%) заявляет сам автор, независимо они не проверены.

### 4.3. pxpipe (teamchong/pxpipe), «сжатие запроса картинками»
- **Простыми словами:** маленькая программа-посредник на компьютере. Между opencode и нейросетью она превращает громоздкие куски запроса в компактные картинки, и в окно контекста помещается больше. Сам ответ нейросети она не трогает.
- **Что сделать:** запуск через `npx pxpipe-proxy` (по умолчанию слушает адрес `127.0.0.1:47821`). Настроить opencode (или OmniRoute) так, чтобы запросы шли через этот адрес. Сделать отдельным переключателем, по умолчанию выключенным.
- **Оговорка:** по собственным тестам автора, часть моделей плохо различает символы при дословной расшифровке плотного текста. Для точных строк и кода это риск, поэтому включать осознанно и сначала проверить на несложной задаче.
- **Проверка:** обычная задача проходит через прокси без ошибок, в окне контекста умещается больше.

### 4.4. auto-improve (crimeacs/auto-improve), «автоматическое улучшение текста»
- **Простыми словами:** скрипт, который сам улучшает любой текстовый файл (промпт, инструкцию, код). Он делает изменённые варианты файла, отдельная независимая модель-судья их оценивает по рубрике, и остаются только изменения, которые реально победили при попарном сравнении с текущей версией. Остальное откатывается. Каждый оставленный шаг это отдельный git-коммит, так что история коммитов и есть журнал улучшений.
- **Это не экономия токенов и не MCP-сервер.** Это отдельный Python-скрипт (`improve.py`, нужен Python 3.9 или новее, зависимости в `requirements.txt`). Он тратит токены на оценку вариантов, поэтому запускать его осознанно.
- **Куда класть:** в `tools/thirdparty`, как rtk, либо сделать скилл в `skills/` (со своим `SKILL.md` и записью в `skills-index.json`), который агент запускает вручную на нужный файл. В реестр MCP его не добавлять.
- **Что сделать:**
  1. Перед работой открыть README репозитория и взять оттуда порядок установки, ключи запуска и настройку модели-судьи. Ничего не придумывать, при составлении плана подробности запуска не проверялись.
  2. Запускать только в отдельной git-ветке: скрипт сам делает коммиты и откаты, и в основной ветке это испортило бы историю.
  3. Ключ модели-судьи хранить рядом с настройками, не в репозитории, и внести в `.gitignore`.
  4. По желанию подключить живой график хода улучшения (маленькая программа на Rust из папки `plot/` репозитория auto-improve). Для этого нужна установка Rust, поэтому по умолчанию не включать.
  5. В программе добавить кнопку «Улучшить файл» с выбором файла и рубрики, по умолчанию выключенную.
- **Проверка:** на тестовом файле в отдельной ветке запускается цикл, появляются коммиты с подтверждёнными улучшениями, неудачные варианты откатываются, основная ветка остаётся нетронутой.

### 4.5. greenlight (RevylAI/greenlight), «проверка iOS-приложения перед App Store»
- **Простыми словами:** консольная программа, которая заранее проверяет iOS-приложение на причины отказа Apple. Она сверяет исходный код, файлы приватности (privacy manifests), собранный IPA-файл и метаданные из App Store Connect с правилами проверки Apple (Review Guidelines). По описанию в README, работает полностью офлайн, без аккаунта, меньше чем за секунду. Лицензия MIT.
- **Это не MCP-сервер и не экономия токенов.** Нужен только если пользователь делает приложения для iOS. Для самого opencode-base (PyQt6, Windows) он не нужен, поэтому делать его отдельной необязательной опцией.
- **Необязательная вторая часть:** команда `greenlight verify` проверяет на облачном устройстве через сервис Revyl, что такие вещи, как удаление аккаунта, восстановление покупок и вход через Apple, реально работают, а не просто написаны в коде. Это отдельный сервис, включать её только по явному желанию пользователя. Основной сканер без неё работает как есть.
- **Установка (по README):** `brew install revylai/tap/greenlight` (macOS), либо `go install github.com/RevylAI/greenlight/cmd/greenlight@latest`, либо сборка из исходников: `git clone https://github.com/RevylAI/greenlight.git`, затем `cd greenlight && make build`, бинарник появится в `build/greenlight`. На Windows путь через Homebrew не подходит, поэтому агенту выбирать `go install` или сборку из исходников, и сначала проверить, что установлены Go и make.
- **Куда класть:** в `tools/thirdparty` как внешнюю программу и оформить скиллом в `skills/` (со своим `SKILL.md` и записью в `skills-index.json`), чтобы агент запускал проверку перед отправкой iOS-приложения. В реестр MCP не добавлять.
- **Что сделать:**
  1. Перед работой открыть README репозитория и взять оттуда актуальные команды и ключи запуска, ничего не придумывать.
  2. Основной сканер запускать только на проекте пользователя, ничего никуда не отправлять.
  3. Если пользователь захочет `greenlight verify`, прямо предупредить, что запуск идёт через сторонний облачный сервис Revyl, и сначала спросить подтверждение.
  4. В программе добавить кнопку «Проверить iOS-приложение перед App Store», по умолчанию выключенную.
- **Проверка:** на тестовом iOS-проекте сканер запускается, выдаёт список найденных рисков по правилам Apple, и в процессе ничего не отправляется наружу.

### 4.6. Qwen Code как второй агент-ревьюер, «вторая пара глаз»
- **Простыми словами:** после того как основной агент в opencode написал или изменил код, второй агент (Qwen Code) читает изменения и ищет ошибки, дыры в безопасности и сомнительные решения. Модель для ревьюера пользователь выбирает сам из списка провайдеров, уже подключённых в opencode. Есть необязательный режим «спор»: ревьюер и основная модель обмениваются доводами, а не просто ревьюер пишет замечания.
- **Основа.** Qwen Code (QwenLM/qwen-code): открытый консольный агент, оптимизированный под модели Qwen. Страница qwen.ai/qwencode при проверке отдала только служебные теги, поэтому порядок установки и ключи запуска агент берёт из README репозитория QwenLM/qwen-code и из официальной документации (qwenlm.github.io/qwen-code-docs), ничего не придумывает. По этой документации, у Qwen Code есть headless-режим (запуск командой `qwen -p "запрос"` без интерфейса), в него можно подать изменения через pipe (`git diff ... | qwen -p "..."`), он умеет выдавать ответ в JSON, есть режимы подтверждений (в том числе режим только планирования), настройки лежат в `~/.qwen/settings.json`, и там можно задать свой адрес API (`baseUrl`) для OpenAI-совместимых провайдеров. Всё это сверить с актуальной версией.
- **Встраивание.** В программе уже есть механизм импорта агентов — Qwen Code встраивается через него же, как ещё один импортируемый агент, а не как отдельный особый случай. Агент-исполнитель сам разберётся, как именно это сделать, глядя на то, как встроены уже существующие агенты.
- **Что сделать.**
  1. Установить Qwen Code по инструкции из README (способ установки не придумывать) и завести его как импортируемого агента через существующий механизм. Кнопка «Включить / Выключить» ревьюера на вкладке «opencode», по умолчанию выключена.
  2. Выбор модели ревьюера: программа показывает список провайдеров и моделей, которые уже подключены в opencode (включая OmniRoute и мост LMArena, если они включены), пользователь выбирает одну. Программа прописывает выбор в настройки Qwen Code (адрес API, имя модели). Ключ берётся из настроек программы и в чат и логи не выводится. Если провайдер из opencode не OpenAI-совместимый, показать пользователю, что для ревьюера он не подходит, а не подставлять наугад.
  3. Основной режим «ревью»: после завершения задачи основным агентом скилл берёт `git diff` изменений, запускает Qwen Code в headless-режиме с запросом на ревью и в режиме без права править файлы (только чтение, режим уточнить по документации). Замечания возвращаются основному агенту и показываются пользователю. Ревьюер сам код не меняет.
  4. Необязательный режим «спор» (по умолчанию выключен, отдельный переключатель):
     - ревьюер присылает замечания, основной агент либо исправляет код, либо возражает с обоснованием;
     - ревьюер отвечает на возражения, и так по кругу, но не больше заданного числа раундов (по умолчанию 3, число меняет пользователь);
     - если за лимит раундов они не пришли к согласию, скилл не решает сам, а показывает пользователю оба довода и спорный фрагмент кода, и решает пользователь;
     - у каждого раунда виден расход токенов, чтобы спор не съел лимиты незаметно.
  5. Скилл положить в `skills/` со своим `SKILL.md` и записью в `skills-index.json`. Qwen Code как внешнюю программу при необходимости положить в `tools/thirdparty`. В реестр MCP не добавлять.
- **Оговорки.**
  - Это не экономия токенов: ревьюер и спор тратят токены дополнительно, особенно в режиме «спор». Для бесплатных моделей это упирается в лимиты, поэтому включать осознанно.
  - Код из `git diff` уходит выбранному провайдеру. Если выбран мост LMArena, действует его предупреждение: приватный код и секреты туда не отправлять, и окно должно говорить об этом прямо.
  - Ревьюер и основная модель могут ошибаться оба, и спор между двумя моделями не доказывает правоту ни одной из них. Окончательное решение за пользователем и за тестами.
  - Модель ревьюера лучше выбирать другую, чем у основного агента, иначе мнения будут слишком похожи.
- **Проверка:** на тестовом изменении в отдельной ветке ревьюер возвращает замечания и не меняет файлы. В режиме «спор» на заведомо спорном фрагменте проходят раунды, после лимита раундов показывается развилка для пользователя, а основная ветка остаётся нетронутой.

## 5. Как встроить всё это в репозиторий opencode-base

Репозиторий: github.com/ccndjfgjs/opencode-base. Программа (окно на PyQt6, `tools/dbapp`) уже умеет подключать сторонние MCP-серверы через блок «6. Серверы MCP» на вкладке «opencode». Новые мосты и инструменты встраиваем в готовые механизмы, а не строим рядом.

Важно для агента: формат записей в `mcp-registry.json` при составлении этого плана прочитать не удалось. Перед работой открыть файл и взять формат из существующих записей (OBS, Android Studio, эмулятор, LDPlayer), ничего не придумывать.

### Куда что ложится

1. **DBHub и браузерный мост (Playwright MCP).** Обычные сторонние MCP-серверы, пакеты которых `npx` скачивает сам. Добавить записями в `mcp-registry.json`: имя, команда запуска, требования для проверки (например, Node.js) и аргументы. Для DBHub нужна форма ввода строки подключения. Пароль к базе хранить рядом с настройками (как пароль OBS), не в репозитории, и передавать серверу через лаунчер в `tools/dbapp/launchers`.
2. **OmniRoute и LMArena.** Отдельные программы, которые надо поднимать. Сделать мост по образцу OBS и эмулятора: код в `tools/thirdparty`, запуск через лаунчер, кнопка «Настроить автоматически» подтверждает результат живым соединением, а не фактом «файл записан». Скилл, который подключает бесплатных провайдеров и умеет перезапускать OmniRoute, положить в `skills/` (папка со своим `SKILL.md`) и внести в `skills-index.json`. Мост LMArena делать так же: код в `tools/thirdparty`, запуск через лаунчер, отдельный скилл в `skills/` с записью в `skills-index.json`, кнопка «Настроить автоматически» подтверждает результат живым ответом модели. Токен арены хранить рядом с настройками и не публиковать. Мост по умолчанию выключен, включается после предупреждения об условиях сервиса.
3. **rtk и caveman.** Это не MCP-серверы. Бинарник rtk положить в `tools/thirdparty`, а подключение к opencode прописать в `config/opencode.jsonc`. Правила caveman вписать в `config/AGENTS.md` либо поставить как скилл. Кнопки «Включить / Выключить» сделать на вкладке «opencode».
4. **pxpipe.** Прокси, а не MCP. Запуск и переключатель «пропускать запросы через него» добавить отдельной опцией, по умолчанию выключенной.
5. **auto-improve.** Python-скрипт, а не MCP. Положить в `tools/thirdparty` либо оформить скиллом в `skills/` с записью в `skills-index.json`. Запуск только вручную и в отдельной git-ветке, ключ модели-судьи хранить вне репозитория.
6. **greenlight.** Консольная программа, а не MCP. Положить в `tools/thirdparty` и оформить скиллом в `skills/` с записью в `skills-index.json`. Нужен только для iOS-приложений, поэтому опция по умолчанию выключена. Часть `greenlight verify` идёт через облачный сервис Revyl и включается только с подтверждения пользователя.
7. **Qwen Code ревьюер.** Консольный агент, а не MCP. Скилл с записью в `skills/` и в `skills-index.json`, выбор модели ревьюера из списка провайдеров opencode, кнопка «Включить / Выключить» на вкладке «opencode», по умолчанию выключен. Режим «спор» отдельным переключателем, тоже выключен по умолчанию.

### Что нельзя ломать

- Пути в конфигах писать пометками (`{{BASE}}`, `{{HERE}}`, `{{DESKTOP}}` и подобными), а не настоящими. Реальные пути подставляет программа при подключении, иначе база не переносится на другой компьютер. Вписывать реальный путь вручную нельзя.
- Повторное нажатие «Включить», когда сервер уже записан, не должно перезаписывать файл настроек: opencode перезапускает все серверы при каждом изменении файла, и лишняя запись поднимает новый экземпляр.
- Пароли и ключи (база данных, провайдеры OmniRoute, токен арены, ключ модели ревьюера) не публиковать: внести в `.gitignore` по образцу уже закрытых секретов.
- Программа не удаляет и не перемещает папки пользователя, не трогает папки проектов и копии, не пишет в служебные папки пакетов (`npm`, `node_modules`) и не меняет чужие файлы настроек, а только добавляет своё или убирает своё.
- Не показывать «зелёную отметку» на пустом месте: если для проверки нужна живая программа (открытая студия, запущенный эмулятор, поднятый OmniRoute), окно должно говорить об этом прямо.
- После изменений прогонять `python tools\dbapp\selftest.py` тем Python, где установлен PyQt6.

## Порядок работы

1. Сначала DBHub (самый простой, готовый сервер).
2. Затем браузерный мост.
3. Затем OmniRoute (больше всего шагов и отдельный скилл).
3а. Затем мост LMArena (по образцу OmniRoute, по умолчанию выключен, с предупреждением об условиях сервиса).
4. Затем rtk и caveman (простые и безопасные).
5. Затем pxpipe (необычный, включать по желанию).
6. Затем auto-improve (отдельный скрипт, запускать вручную и только в отдельной git-ветке).
7. Затем greenlight (нужен только для iOS-приложений, необязательная опция).
8. В конце Qwen Code ревьюер (нужны уже подключённые провайдеры, поэтому после пунктов 3 и 3а; режим «спор» включать только после проверки обычного ревью).

Каждый пункт сразу встраивать в opencode-base по разделу 5, а после каждого пункта делать проверку по описанию выше и только потом переходить к следующему.
